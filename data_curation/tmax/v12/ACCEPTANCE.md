# V12 acceptance — validation plan and hand dry run (2026-09-18)

Standard: per-axis criteria, applied to V12's rule ids. Judge: `claude-opus-4-8`, effort `medium`, explicit per call;
runner contract unchanged except for one added input (batch file → per-task row file → labels-only return; the runner
substitutes `{TASK_ROOT}`, `{OUTPUT_PATH}` and **`{CANDIDATES_PATH}`** per task and validates each row against
`output_schema_v12.json` with `Draft202012Validator`; the judge may run its own arithmetic with the named interpreter
and never the task's scripts). Rule ids are DESIGN §e / prompt §4: A1 `oracle_reachable`, A2 `expectation_revealed`,
A3 `value_derivable`, A4 `expectation_movable`, A5 `untouched_image_passes`, A6 `weak_verifier_exploit`, A7
`core_clause_unenforced`, B1 `overspecific_check`, B2 `env_mismatch` / `unconfirmed_dependency` (the hold), B3
`unstable_reward`. Scoring: schema + the lints L1–L15 of DESIGN §h (`validation/lint_v12.py`, run with
`--candidates validation/candidates`) + the per-axis checks below; `validation/schema_selftest.py` reports
ALL EXPECTATIONS HOLD and the ten exemplar rows in `validation/dryrun_rows/` are schema-valid and lint-clean.

## 0. Decisions that shape the plan

- **The inventory is supplied, not self-certified.** Each judge reads `validation/candidates/<task_id>.json`
  (`programs`, `failing_statements`, `test_sh_lines`, `imports`) and must dispose of every `programs` entry — an
  `excluded_material` row (including the new `benign`) or a Step-3 rule field — and cover every `failing_statements`
  line with an `assertions` entry. L13 and L14 check both; an omitted oracle is no longer an invisible escape.
- **REPAIR vs REJECT-PROVEN is a named shape, not a cost.** `verifier_fix` is a change confined to tests/test.sh or
  `null`; the `none: <reason>` string is gone, and `repro_cost` moves no tier. REJECT-PROVEN requires
  `reject_shape` ∈ {`instruction_prints_answer`, `deliverable_is_leaked_material`, `broken_premise`, `pre_solved`}
  with `verifier_fix` null; a fired floor with a fix — **including a partial fix whose residue is a rollout copy** —
  is REPAIR; a fired floor with neither fix nor shape is REVIEW. Pre-registered discard: **000241,
  `deliverable_is_leaked_material`** (the recovered file is static and byte-reproducible from the readable
  deterministic generator, and no test.sh change makes that reconstruction score 0). **000311 is accepted in either
  class**: REJECT-PROVEN under the same shape when the judge's reproduction includes the one-line awk fix (its final
  state is then indistinguishable from the faithful one), or REPAIR when the reproduction is the two leaked literals
  and the judge names the grade-time run of the pinned `build.sh` that makes it score 0 — the class turns on which A3
  reproduction the row records, which Step 8 leaves to the judge. Every other guard is REPAIR.
- **Dependency-held rows are tier PASS.** `unconfirmed_dependency` is a recorded fact with no tier consequence
  (DESIGN B2, §f). A PASS row carrying it is *PASS-held*; the scorer reports PASS-clean and PASS-held separately, and
  the four PASS-required controls must all be tier **PASS** (two of them held) until the base-image probe releases or
  converts the class. A module the task itself ships is not a hold (Step 0, lint L8).
- **The two sides report separately.** `exploit_status_a` (A1–A7, A5 `yes`, D) and `exploit_status_b` (B1–B3): a
  fired B rule with a named fix sets REPAIR whatever the A side could drive, and a side that fired nothing is
  `none_found` (schema I4).
- **Method clauses stay secondary.** A language, packaging, path or format clause around a content-checked result is
  recorded in `secondary_clauses_unenforced` and routes nothing unless the instruction states that the method is the
  purpose. The ten FINE controls therefore keep the expectations the best-measured baseline established (§3), and
  there is **no retention target** anywhere in this plan: over-filtering is measured by the pre-registered controls
  and movers of §4, never by a count the rubric could satisfy by returning it.

## 2. task_004886 and the runtime receipt

`untouched_image_passes: yes` is a runtime fact (the shipped release binary scores 1). A static judge cannot see it:
the only assertion the shipped state could fail is the 2.0 s wall-clock, so A5 (ii) case (a) requires `unknown` and
forbids `no` (an instruction's claim about runtime is not an assertion outcome the files fix). Accepted values:
`yes: …` and `unknown: …`; `no: …` is a failure. With `unknown`, the tier is still REPAIR: A2/A3 fired with a
runnable reproduction (copy the golden file) and Step 9.2 keeps the floor's tier; `reason` must request the empty run.
A REVIEW here is a failure unless neither side is `static_trace`.

**Disagreement rule (k = 2 on G).** The two repeats must agree on (a) non-PASS for the guards, (b) the set of floor
rule ids named, (c) that each floor field names an accepted path for that rule, (d) the pre-registered tier class.
Tolerated variance: REPAIR ↔ REVIEW when one repeat drives nothing; an additional rule field beyond the required
ones; different wording, cost or fix text; `exploit_status_b` `not_applicable` ↔ `static_trace` when both sides
fired. Not tolerated: REPAIR ↔ REJECT-PROVEN against the pre-registered class (000311 excepted: both classes are
pre-registered there, and a split across its two repeats is a recorded property of the criterion, not a failure); a
required floor rule missing in some repeat; a path outside the accepted set; a `reject_shape` on a row §1
pre-registers as REPAIR. When the two repeats
fill the *rule fields* differently on identical input the rubric is at fault (the predicate is not mechanical enough);
when only free text, cost or fix wording differs it is judge noise and does not fail the run.

**Row lints, every row** (DESIGN §h, `validation/lint_v12.py --candidates validation/candidates`): schema-valid; L1
floor paths are tokens of the three files; L2 / L2b the assertion census; L3 excluded paths disjoint from the leak
paths and no mislabelled `toolchain`; L4 no secondary clause names a floor path; L5 no backslash-n inside a quoted
`python3 -c`; L6 an A5 `no:` cites a non-timing line; L7 `evidence_line` in range and an assertion line for the
strong rules; L8 the held-dependency inventory; L9 the per-assertion outcomes; L10 compiled programs the instruction
names are inventoried; L11 anchors in range; L12 the hold is the only channel; **L13 every `programs` candidate
disposed of; L14 every `failing_statements` line covered; L15 `derivation_is_core_step` cites a `core_step` entry**.
A lint violation is an invalid row and fails the run regardless of tier. The rubric is at fault when one lint fires on
more than 3 rows (a systematic wording problem), the judge when it fires sporadically. L13/L14 are the two this run
exists to measure: they replace the inventory the judge used to certify for itself.

**The over-rejection instrument (the run fails when any clause fails).**
1. All four PASS-required controls (000316, 001104, 000854, 005042) are tier PASS or PASS-held in **every** repeat.
2. The leak axis is clean on **all ten** controls in every repeat (no `oracle_reachable`, `expectation_revealed` or
   `value_derivable`, and verdict ≠ ANSWER-LEAK).
3. On the movers, 000092 and 006700 are PASS.
4. No row carries `reject_shape` outside the four enum values, and no REJECT-PROVEN row exists whose `reason` does
   not state the shape's condition (read by the scorer, reported per row).
The instrument is deliberately not a retention count: a rubric cannot satisfy it by admitting the wrong tasks,
because clauses 1–3 name the tasks and clause 4 names the burden a discard carries.

**Reported alongside (not pass/fail):** the tier distribution over the 70; REJECT-PROVEN rows by shape; REVIEW rows
split by trigger (nothing driven / no fix and no shape / uncertain fact / unknown / unverified / ambiguity); the
per-side statuses; PASS-clean vs PASS-held; lint hits per id; and, on the ids shared with the earlier baseline run,
the tier comparison with `../v10_1/validation/RESULTS_draft1.md`.
