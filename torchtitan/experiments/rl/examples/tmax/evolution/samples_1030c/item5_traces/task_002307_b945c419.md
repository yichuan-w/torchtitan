## Primary sources and reproduced behavior

- https://www.rfc-editor.org/rfc/rfc4180.txt — RFC 4180 says: “Common usage of CSV is US-ASCII, but other character sets defined by IANA for the ‘text’ tree may be used in conjunction with the ‘charset’ parameter.” This establishes that CSV is not intrinsically UTF-8.
- https://raw.githubusercontent.com/python/cpython/v3.10.12/Doc/library/json.rst — Python 3.10.12's JSON documentation says JSON input encoding should be UTF-8, UTF-16, or UTF-32, and that UTF-8 is the recommended default. JSON therefore remains standards-conforming while the CSV side carries the legacy-encoding difficulty.
- https://raw.githubusercontent.com/chardet/chardet/5.2.0/docs/usage.rst — chardet 5.2.0 documents that `detect` takes a non-Unicode byte string and returns an auto-detected encoding and confidence, giving an investigating student a real tool rather than a task-authored hint.
- https://pypi.org/pypi/chardet/5.2.0/json — PyPI identifies the pinned 5.2.0 sdist at `https://files.pythonhosted.org/packages/f3/0d/f7b6ab21ec75897ed80c17d79b15951a719226b9fababf1e40ea74d69079/chardet-5.2.0.tar.gz` with SHA-256 `1b3b6ff479a8c414bc3fa2c0852995695c4a026dcd6d0633b2dd092ca39c1cf7`.

Pinned artifact: `chardet==5.2.0` from the above PyPI release. It will be installed during image build; the task input, not a vendored imitation, exhibits the real decoding behavior.

Reproduction in the current Python 3.10.12 image:

Observed output: `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe9 ... invalid continuation byte` (exit 1).

## Proposed change and new decision

Add two ordinary CSV exports whose bytes use different real legacy encodings. One contains a Windows-1252-only printable character, so treating all failing files as ISO-8859-1 is wrong without crashing; the canonical JSON must preserve the decoded text. Install the pinned upstream detector as an investigation tool. The student must inspect bytes/detection results, choose decoding per file, run the ETL, and validate Unicode output. This is one modest step beyond the attempts' existing file inspection and Python ETL workflow, and is real configuration-export recovery work rather than another schema edge case.

The original wording will be retained and extended only to state the observable requirement that source text may use different encodings and must be preserved. No prior simplification help exists to withdraw.

## Shortcut trials and trace replays

The revised image reproduced both failures under Python 3.10.12. Reading either new file as UTF-8 raises `UnicodeDecodeError`; chardet 5.2.0 reports `ISO-8859-1` for `logs_C.csv` and `Windows-1252` for `logs_D.csv`, each with confidence 0.73.

I tested two likely first fixes, each from a fresh reset:

1. Opening all CSV as UTF-8 with `errors="ignore"` completed but `./sandbox grade` returned 0. The content check showed `café` became `caf` (and the em dash was also discarded), so suppressing the error does not preserve text.
2. Opening every CSV as `latin-1` completed but `./sandbox grade` returned 0. The content check showed the Windows-1252 em dash became the C1 control character `\\x97`, so one plausible legacy codec does not handle both sources.

I then replayed the exact shell commands of `traces/attempt-01.jsonl` from a fresh reset. It stopped when `csv.DictReader` first consumed `logs_C.csv`: UTF-8 decoding raised `UnicodeDecodeError`; no output or log existed. The grade returned 0 and failed the output existence/content check (therefore logging was not reached). I repeated this with `traces/attempt-12.jsonl`: it stopped at the same UTF-8 decoding exception, produced neither output nor log, and the grade returned 0 at the output existence/content check.

Both prior strategies are directly interrupted, while the visible Unicode error plus byte-level inspection and the installed detector provide a bounded investigation path. I expect **6 of 12** in the next group: successful attempts must react after their first run, inspect more than the filenames/schema, choose per-file decoding rather than merely suppressing errors or applying one codec globally, and rerun the otherwise familiar ETL.
